# Audit A — Numbers forensics

## Verdict (1 paragraph)

The email's 8 complaints are explained by **three structural bugs and one structural taxonomy gap**: (1) a parquet-join duplication of `bacino` (one bacino value gets multiplied by N channels in `daily_aggregated.parquet`), which the WIP commit `7ea4a74` partially mitigates by dividing back by `n_channels` — and that mitigation reproduces the email's "Sentinel: 133M / 41.8% / 2.08 / 0.87 / 115k" exactly; (2) all revenue/eCPM/RPM displayed as **net (post 60% rev-share)** without any UI label, while PBI shows **gross** (e.g. Mondadori Feb gross = €192,651 ≈ PBI €188k; Sentinel net = €115,591); (3) `revenue_status_24h` reads only `hourly_aggregated.parquet` which is a **single-channel file (GOOGLE_ADEX only)**, with no UI badge disclosing the scope, and the YoY hourly curve is **synthesized by reshaping a daily total** through the current baseline's hourly proportions (`routes.py:740-745`). Plus a publisher-id taxonomy gap: PBI's "Mondadori" group (366M) is plausibly Mondadori (133.6M ad-requests upstream) + Mondadori_npa (162.6M) + sub-units like Adgage_mondocore (109.9M); Sentinel reports each `publisher_id` separately. The WIP commit `7ea4a74` is in the **correct direction** for bacino dedup but only as a workaround — the parquet itself is structurally wrong (bacino should not be a per-channel column in the joined output). Cross-cutting: the 24-hour hourly dashboard and the alert payloads are mostly net-revenue + AdEx-only, but neither fact is surfaced in the UI, which is the proximal cause of every Mondadori-row mismatch in the email.

### Direction assessment

**The WIP fix is in the CORRECT direction**: pre-WIP raw sum massively over-counts bacino due to N-fold join duplication; the WIP `/n_channels` divide approximately recovers the correct per-(pub,date,env,geo)-cell bacino. For cells where bacino is uniform across channels (most cells: see A.4 #1 evidence), the divide produces the exact upstream `daily_adrequests.csv` value.

**However, the WIP fix is NOT what the email asks for**: the email's complaint is "133M Sentinel vs 366M PBI — please match PBI". The WIP fix produces 133M (which already matches Sentinel email's number). To match PBI's 366M, the WIP fix would need to be REVERTED OR a different aggregation (group multiple publisher_ids; show gross instead of net; bypass top-50 parquet filter — which is what API-01 hybrid endpoint was supposed to do).

**Caveat — the WIP fix has a math defect** for cells where bacino is non-uniform across channels (98 of 237 Mondadori Feb cells, mostly WEB/OTHER geo cluster):
- For uniform cells (e.g. WEB/ITA Feb 1: 6 channels, all bacino=5,708,992) → WIP fix divides 6×5708992 / 6 = 5,708,992. CORRECT.
- For non-uniform cells (e.g. WEB/OTHER Feb 1: 6 channels, bacinos ranging 2…63,054) → WIP fix divides sum / 6, which equals MEAN. This is an arbitrary aggregation, not "the true bacino". A better approach would be `MAX` per cell or `unique`-then-sum.

## A.4 Formula bugs identified

### Bug 1 — `publisher_routes.py:200-207` — `bacino` n_channels divide is a workaround, not a structural fix

Pre-WIP (`7de84ab`): `total_bacino = ('bacino', 'sum')` over-counts because `bacino` is replicated across channels in the join (parquet origin: `etl_csv_to_parquet.py:213-218` left-joins `daily_kpi.csv` (per-channel) with `daily_adrequests.csv` (per-publisher-day-env-geo, no channel_group), so the single bacino value gets duplicated across each of the 7 channel rows for that publisher-day-env-geo cell).

Post-WIP fix divides by `n_channels`, which is correct only for cells with uniform bacino across channels. For 98/237 Mondadori Feb cells the bacino values differ across channels (likely because some channels didn't run that day), and the division becomes `MEAN` rather than `DEDUP`.

**Cleaner formula:** `bacino_per_cell = df.groupby([pub,date,env,geo])['bacino'].max()` (taking the canonical per-cell bacino value, since when uniform max==value, when non-uniform max gives the true total available inventory).

### Bug 2 — `publisher_routes.py:186, 221, 264` — revenue is NET (post 60% rev-share) but UI label says just "Revenue"

`agg_dict["total_revenue"] = ("revenue", "sum")` aggregates the `revenue` column which `etl_csv_to_parquet.py` `apply_revenue_share` populates as `revenue_gross * pub_share` (default 0.60). PBI shows GROSS by default. The parquet HAS `revenue_gross` (line 195-196 conditionally aggregates `total_revenue_gross` but it's never returned in the response — see lines 274-292 publisher entry construction).

Mondadori Feb gross/net split: gross €192,651 / net €115,591 → ratio 0.5999. Email's PBI €188k ≈ Mondadori-only gross (€192k). **Adding `revenue_gross` to the response is the correctness fix** for complaint 4e.

### Bug 3 — `publisher_routes.py:200-211` — `/api/publishers/top` annual filter, no Feb-specific endpoint

`df_year = df[df["date"].dt.year == year]` filters by **calendar year only**. There is no "month" or "date_range" param. The email's "Mondadori Feb" comparison is operator-side: presumably comparing Sentinel publisher row YTD vs PBI Feb-only. **No backend bug here, but a UI/UX gap** — Sentinel cannot show "publisher KPIs for February 2026 only" via `/top`.

### Bug 4 — `TriageSection.tsx:29-32` — frontend baseline heuristic invented from thin air

```typescript
const revenueRatio = alert.revenue_current ? alert.revenue_baseline / alert.revenue_current : 1
const baselineBacino = Math.round(totalBacino * (revenueRatio * 0.95))
const baselineCoverage = Math.min(avgCoverage + 0.05, 0.95)
```

Both `baselineBacino` and `baselineCoverage` are **fabricated client-side**: bacino baseline = current bacino × (revenue_ratio × 0.95); coverage baseline = current coverage + 0.05 capped at 0.95. Neither is from the database; both are heuristic guesses. Email complaint #4b ("fill rate non torna") is partially this: the displayed "Coverage current vs baseline" delta is meaningless because the baseline is `current+5pp`. Fix: API-03 server-side baseline (CORR-01).

### Bug 5 — `routes.py:740-745` — hourly YoY is a synthetic reshape of daily total

The "hours" array in `prev_year` payload is constructed by multiplying a single `py_rev` daily total by the **current year's baseline hourly distribution proportions**. This is not measured PY hourly data — it's a fabrication. Email correctly notes "YoY orario non dovrebbe essere nella base dato".

### Bug 6 — `routes.py:619-768` `revenue_status_24h` — single-channel scope (GOOGLE_ADEX only) silent

`_load_hourly_data()` reads `hourly_aggregated.parquet` which is **single-channel** (GOOGLE_ADEX-only by upstream `hour_kpi.csv` limit per PROJECT.md "Out of Scope"). The endpoint does NOT filter by channel because the parquet has only one. The frontend renders this as "Revenue Status 24h" with no channel scope badge. Email complaint #1 is partly this: PBI Hour Analysis includes Open Market = AdEx + OPEN_BIDDING; Sentinel hourly shows AdEx only.

### Bug 7 — `routes.py:619-768` revenue is net but label is just "Revenue"

Same as Bug 2 but at the hourly endpoint. `total_revenue` is `df['revenue'].sum()` post-rev-share (net). PBI Hour Analysis is gross. Mismatch of 1.66× (since rev-share = 0.60).

### Bug 8 — Alert payloads: `revenue_current` has no temporal reference

`schemas.AlertDetail.revenue_current: float` (no period field). Operator sees "€25,927" with no "as of [hour] UTC" or "trailing 24h" label. Same complaint #5 in email.

### Bug 9 — `routes.py:230` `get_alert_trend` — no diagnostic empty state

When the alert's `channel_group='GOOGLE'` (legacy), `_load_daily_channel_data` returns the legacy parquet which has GOOGLE up to 2026-01-22. For dates after, `filtered = df[mask]` is empty, daily aggregation produces empty result, frontend shows "No revenue trend data available" without explaining why (channel naming mismatch). Email complaint #6.

### Bug 10 — Publisher-id taxonomy not aligned with PBI

PBI's "Mondadori" rolls up multiple internal ad_unit_ids; Sentinel's parquet preserves Mondadori and Mondadori_npa as separate publisher_ids. Mondadori (133.6M) + Mondadori_npa (162.6M) = 296.2M, still short of PBI's 366M. Possible additional roll-ups: Adgage_mondocore (109.9M). Without PBI's mapping doc, exact reconciliation is impossible.
