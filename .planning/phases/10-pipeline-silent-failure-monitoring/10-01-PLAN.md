**Meta-alert scheduling location (Phase 10 per-phase decision for plan 10-03 but logged here because it informs 10-01 column semantics):** chose option (c) — dedicated module `backend/monitoring/silent_failure_watch.py` invoked by scheduler — per R-13 watertight boundary. Options (a) APScheduler-in-scheduler.py and (b) orchestrator-tail-hook rejected: (a) bloats scheduler.py (already 286 lines, 5 jobs registered) and couples monitoring to scheduler internals; (b) creates a run-by-run coupling that misses the "many runs, 0 alerts" pattern (the watchdog needs the aggregate 24h view, not per-run). Option (c) keeps the watchdog as a single-responsibility module consumed by scheduler via a clean cron hook.

**Counter semantics — alerts_written_count INT vs BOOL:** chose INT with CHECK(>= 0) not BOOL. Rationale: while in v1.3 each pipeline run writes at most 1 alert, the pipeline may evolve to emit multiple alerts per run (e.g., A5+A6 co-fire path in anomaly_detector). INT preserves that headroom without schema re-migration. BOOL would force a future migration if ever changed.

**Column position — last vs mid-table:** chose LAST (after `created_at`). Per Phase 09 I-2 precedent: SQLite ALTER TABLE ADD COLUMN appends to the schema definition; placing the column anywhere else in SQL_CREATE_PIPELINE_RUNS would cause a byte-identity drift the HARD-03 gate catches. Placing it last = both gate-safe and consistent with post-ALTER sqlite_master layout.

**Backfill of pre-existing pipeline_runs rows:** chose "leave at DEFAULT 0, do NOT retro-fill". Rationale: the pre-existing rows (≥1,442 per Phase 09 snapshot; exact count drifts upward as the scheduler keeps writing) are from the Phase 09 backfill (BACKTEST mode) and from the 2-month LIVE silent-failure window — they legitimately have `alerts_written_count=0` (either BACKTEST never wrote alerts by spec, or LIVE runs failed silently). Retro-filling from `alert_id IS NOT NULL` would muddy the signal the watchdog needs. Fresh data from Phase 10 forward will populate correctly.
