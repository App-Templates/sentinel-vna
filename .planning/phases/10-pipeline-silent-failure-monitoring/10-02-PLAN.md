<objective>
Implement `GET /api/health/alerts-pipeline` endpoint (MONITOR-01) that exposes three metrics consumable by external monitors and (in Phase 10-03) by the internal meta-alert watchdog:
- `last_alert_at`: most recent non-deprecated alert's `created_at` timestamp.
- `alerts_last_24h`: count of non-deprecated alerts created in last 24 hours.
- `pipeline_runs_last_24h`: count of pipeline_runs records created in last 24 hours.

Purpose: the silent-failure pattern of 2026-01-22 → 2026-04-22 manifested as "pipeline_runs growing, alerts frozen". This endpoint makes that pattern OBSERVABLE via a single HTTP call suitable for external monitoring (UptimeRobot, Pingdom, synthetic probes). Phase 10-03 polls this endpoint (or its underlying operation) on a cron and emits a Slack P0 on the divergence.

<alternatives_considered>
**Endpoint location — same routes.py vs new health_routes.py:** chose same `backend/api/routes.py` (append below existing `/health` handler). Rationale: `/health/alerts-pipeline` is conceptually a health endpoint extension, not a new module. routes.py is large (800+ lines) but adding 1 endpoint is ~30 lines; splitting prematurely would fragment the health surface. A dedicated `backend/api/health_routes.py` module becomes justified in Phase 14/15 if total health endpoints exceed 3. For Phase 10 with 1 new endpoint, single file is R-13-compliant (watertight boundaries aren't violated — both /health and /health/alerts-pipeline live in the same "health" concern).

**Time source — `datetime('now', '-1 day')` SQLite vs Python datetime.now() - timedelta:** chose SQLite builtin. Rationale: `get_pipeline_metrics` (operations.py:297-309) already uses this pattern — consistency matters more than marginal perf. SQLite-side time math also avoids client/server clock drift when queries run inside transactions.

**Response caching:** deliberately NO caching. Each request executes 3 SELECT queries (est. <50ms on live DB). Caching introduces staleness that would defeat the purpose of a silent-failure watchdog probe. If load becomes an issue (implausible for internal monitor), consider a 30s TTL in Phase 11.

**Alert query semantic — include deprecated?:** chose NO, `WHERE deprecated = 0`. Rationale above in `<interfaces>` Legacy filter note. Deprecated alerts are historical context, not current signal. Watchdog wants "are we still writing alerts?" — deprecated=1 alerts from Phase 09 legacy migration are not evidence of liveness.

**Include `alerts_written_count` aggregate in response?:** No. The response contract is frozen by REQ MONITOR-01 at `{last_alert_at, alerts_last_24h, pipeline_runs_last_24h}`. Adding a fourth field (e.g., `sum(alerts_written_count)_last_24h`) would be a requirement-creep. The counter is populated (Plan 10-01); the watchdog (Plan 10-03) can query it directly from operations helpers. Keep endpoint contract minimal.
</alternatives_considered>

    ```
    def get_alerts_pipeline_health() -> dict[str, Any]:
        """Return silent-failure watchdog metrics (MONITOR-01, Phase 10).

        Returns {last_alert_at, alerts_last_24h, pipeline_runs_last_24h}.
        - last_alert_at: MAX(created_at) from non-deprecated alerts, or None if empty.
        - alerts_last_24h: COUNT of non-deprecated alerts created in last 24h.
        - pipeline_runs_last_24h: COUNT of pipeline_runs rows created in last 24h.

        Query budget: < 5 seconds on the live DB (3 indexed-or-small-scan SELECTs).
        Consumed by:
          * GET /api/health/alerts-pipeline (backend/api/routes.py)
          * backend/monitoring/silent_failure_watch.py (Phase 10-03)
        """
        with get_db() as conn:
            # 1. last_alert_at — MAX created_at from non-deprecated alerts.
            #    Uses idx_alerts_deprecated (Phase 09 migration 002) + full scan over
            #    created_at (no index on created_at for alerts; 438 rows — acceptable).
            row = conn.execute(
                "SELECT MAX(created_at) FROM alerts WHERE deprecated = 0"
            ).fetchone()
            last_alert_at = row[0] if row is not None else None

            # 2. alerts_last_24h — 24h sliding window of non-deprecated alerts.
            row = conn.execute(
                """SELECT COUNT(*) FROM alerts
                   WHERE deprecated = 0
                     AND created_at >= datetime('now', '-1 day')"""
            ).fetchone()
            alerts_last_24h = int(row[0]) if row and row[0] is not None else 0

            # 3. pipeline_runs_last_24h — 24h sliding window; uses idx_pipeline_runs_created.
            row = conn.execute(
                """SELECT COUNT(*) FROM pipeline_runs
                   WHERE created_at >= datetime('now', '-1 day')"""
            ).fetchone()
            pipeline_runs_last_24h = int(row[0]) if row and row[0] is not None else 0

        return {
            "last_alert_at": last_alert_at,
            "alerts_last_24h": alerts_last_24h,
            "pipeline_runs_last_24h": pipeline_runs_last_24h,
        }
    ```

    Ensure `Any` is imported from `typing` (already used throughout operations.py — no change).
