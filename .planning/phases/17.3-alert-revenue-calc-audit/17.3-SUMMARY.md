## Accomplishments

1. **Root cause confirmed (Task 1):** Both sample alerts' DB revenue values match the synthetic generator byte-for-byte. The pipeline tz-mismatch causes silent fallback to synthetic data in BACKTEST mode. All ~2160 backfill alerts (Phase 09) are affected. Reproduction script in DIAGNOSIS.md.

2. **RED regression test (Task 2):** `scripts/test_alert_revenue_hourly_window.py` pins 4 invariants. 2/4 RED pre-fix (the data_source='real_parquet' invariants); 4/4 GREEN post-fix.

3. **GREEN fix (Task 3):** `backend/agents/data_fetcher_real.py:~589` now strips tzinfo from `current_ts` before parquet comparison. Single-point chirurgico fix. All 4 invariants now GREEN. No regression on existing 17.1/17.2 test suites (publisher drilldown 9/9 OK, triage baseline OK, alert sections payload contract OK).

4. **Structural findings documented (Task 5):** Even with the code fix, the 2 sample alerts CANNOT show ±2% PBI match because:
   - **Sample 1 (GOOGLE_ADEX 2026-03-22 01:00):** parquet returns €521.44 gross / €312.87 net vs PBI €662.67 gross. 21.3% off due to **top-50 publisher filter** in `daily_aggregated.parquet` (Phase 11 D1 hybrid trade-off). Closing this requires re-aggregating parquet without the filter or implementing the Phase 11 `/api/metrics/network-totals` style endpoint at the alert-detail layer (Phase 18 candidate).
   - **Sample 2 (HEADER_BIDDING_MAGNITE 2026-03-20 07:00):** parquet has **zero** HBM hourly rows — `data/sentinel_db/hour_kpi.csv` upstream contains only GOOGLE_ADEX. Closing this requires expanding upstream hourly ingestion to 8 channels (v1.4 Athena territory, OR Marco-provided HBM hourly dump).

5. **Deploy decision (Task 4 deferred):** Existing DB rows are unchanged by the code fix (the fix affects FUTURE alert generation only). The Vercel snapshot regenerated today would be byte-identical to the current production snapshot for these 2 alert IDs. Therefore deploy has zero user-visible delta and is deferred per R-04 chirurgico — ship code with next phase that has actual UI/data delta.

## Decisions Made

1. **Root cause = H6 (NEW), refuting H1-H5 ranked in CONTEXT.md.** The hypothesis-driven planning was correct methodology but the actual cause was a tz-aware/tz-naive pandas silent-False comparison, not multi-hour window or channel filter mismatch. Synthetic byte-match to DB values is the empirical evidence.

2. **Fix scope = 1 line (chirurgico).** Defensive alternative (normalize parquet load to tz-aware) was rejected — that would touch a column read used by all consumers and could regress other paths. Single normalization at the data_fetcher_real boundary is the minimum blast radius.

3. **No re-backfill of historical alerts.** Risks: (a) invalidates Marco's reference baselines (the very alerts Marco audited would change values), (b) for GOOGLE_ADEX the new values would still be 21% off PBI due to top-50 filter, (c) for HBM/HBP/TAM/etc the new values are still synthetic (no upstream source). The fix benefits future alerts; historical ones documented as "synthetic-revenue era — Phase 09 backfill 2026-04-23 to 2026-05-21".

4. **No Vercel deploy this phase.** The fix changes code, not data. Existing DB rows are untouched. The snapshot would be byte-identical for the 2 sample alerts and for all other ~2160 backfill alerts. Per R-04, no chirurgico justification for a deploy with zero user-visible delta. Next phase (18, or 17.4 if Marco escalates) ships this fix along with its own visible deltas.

5. **AUDIT-01..03 requirements satisfied by audit + fix + test, not by closing the PBI numerical match.** Phase scope was "explain and document the discrepancy + land minimum fix + regression test"; success criteria #3 ("revenue gross post-fix coerente con PBI ±2%") is unmeetable due to documented structural gaps and is downgraded to "documented as known limitation with phase-18 / v1.4 follow-up paths".
