# Phase 17.3 — Alert Revenue Calculation Diagnosis

## TL;DR

Both sample alerts (`ALT-20260322-010000-P2`, `ALT-20260320-070000-P2`) carry `revenue_current` values that are **100% synthetic** — generated by `backend/agents/data_fetcher.py:_generate_hourly_metrics()` from the deterministic `HOURLY_PATTERN` × `BASE_HOURLY_REVENUE` × `A2 anomaly_factor (0.92)` × `_seeded_noise`. The parquet (real CSV-derived data) is **never consulted** for any backfill-generated alert because of a **silent timezone-mismatch bug** in `backend/agents/data_fetcher_real.py`.

The numbers Marco compares against PBI (€736, €1185) are therefore **fictional values** — they cannot be reconciled with PBI by tuning a window or channel filter, because they don't come from any real measurement at all. Sentinel is currently presenting synthetic placeholders to operators.

This is **NOT H1 (multi-hour window)** nor **H2 (channel filter mismatch)** as ranked in CONTEXT.md. It is a new hypothesis: **H6 — silent synthetic-fallback via tz-mismatch in BACKTEST mode** (parent pipeline of `scripts/backfill_alerts.py`).

### 7. Synthetic generator — deterministic formula

`backend/agents/data_fetcher.py:94-180`

```python
HOURLY_PATTERN = [0.15, 0.10, 0.08, 0.07, 0.06, 0.08, 0.20, 0.45, 0.65, ...]  # 24 entries
BASE_HOURLY_REVENUE = {"GOOGLE_ADEX": 12000.0, "HEADER_BIDDING_MAGNITE": 3000.0, ...}

def _generate_hourly_metrics(ts, channel, anomaly_config):
    hour_mult = HOURLY_PATTERN[ts.hour]
    dow_mult = DOW_PATTERN[ts.weekday()]
    noise = _seeded_noise(f"{ts.isoformat()}-{channel}", scale=0.08)
    base_rev = BASE_HOURLY_REVENUE.get(channel, 10000.0)
    revenue = base_rev * hour_mult * dow_mult * (1 + noise)
    # A2 anomaly: revenue_factor=0.92
    if anomaly_config and anomaly_config.get('active'):
        revenue *= anomaly_config['revenue_factor']
    return {..., "revenue": round(revenue, 2), ...}
```

For Sample 1: `12000 × 0.10 × DOW(Sun=0.65) × (1+noise) × 0.92 = ~736`
For Sample 2: `3000 × 0.45 × DOW(Fri=0.95) × (1+noise) × 0.92 = ~1185`

The values match the DB **byte-for-byte** because the synthetic generator is deterministic (md5 noise).

## Why the synthetic values look plausible

The `hh = channel_idx * 3 + trigger_idx` encoding gives `hh ∈ [0, 23]`. The synthetic generator uses `ts.hour` as index into a 24-element HOURLY_PATTERN. So every backfilled alert *happens* to evaluate a real hourly bucket on the synthetic curve, even though the timestamp's "hour" was never meant to be wall-clock. This makes the values look like reasonable EUR amounts (€100–€2000 range) instead of clearly broken ones.

Combined with the synthetic A2 anomaly factor (0.92) and the day-of-week multiplier (DOW_PATTERN[weekday]), the output passes a "looks like real ad revenue" sanity check — exactly the kind of plausible-looking failure that escapes operators' notice until Marco does a numeric audit against PBI.

## Recommended fix (this phase: MINIMAL chirurgico)

**FIX-1 (Rule 1 bug — tz alignment):**

In `backend/agents/data_fetcher_real.py`, ensure `current_ts` is **tz-naive** before any parquet comparison:

```python
# Line ~589 (after D6 round-to-hour):
current_ts = current_ts.replace(minute=0, second=0, microsecond=0)
# NEW: align with parquet timestamp tz (tz-naive)
if current_ts.tzinfo is not None:
    current_ts = current_ts.replace(tzinfo=None)
```

Alternative (more defensive — normalize at parquet load):

```python
# Line ~75:
df['timestamp'] = pd.to_datetime(df['timestamp'])
# ← Both sides become tz-naive UTC by convention; assert no tz drift downstream.
```

The first option is preferred (chirurgico, single point of fix, no parquet schema implication).

## Lessons learned

- Silent fallback to synthetic with no provenance in DB (`data_source='backfill'` masks `data_source='synthetic'`) made the bug invisible to operators for **months** (since Phase 09 backfill 2026-04-23). Auditor surfaced it only via PBI cross-check, exactly the kind of discrepancy a contract test should have caught.
- The `hh = channel_idx * 3 + trigger_idx` encoding in `backfill_alerts.py` is fragile: the encoded "hour" looks like a real hour-of-day, both to the synthetic generator (which indexes `HOURLY_PATTERN[hh]`) and to Marco reading the alert ID. A separate `alert_seq` field or non-encoded disambiguation would have been clearer.
- Phase 11 D1 (top-50 filter / `/network-totals` endpoint) is a known structural limitation. With FIX-1 the alert revenue will drop from "deterministic synthetic" to "real-but-top-50-limited", which means **all alert revenue values will change post-fix** (decrease for GOOGLE_ADEX, become unavailable / synthetic-disclosed for HBM-class channels). This is the trade Marco asked for: real numbers > fictional numbers.
