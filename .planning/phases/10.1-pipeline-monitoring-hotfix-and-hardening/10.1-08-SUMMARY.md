## Phase 10.1 Closure Narrative

### MONITOR-0{4..8} → Plan mapping

| MONITOR | Bug class | Fix | Plan |
|---------|-----------|-----|------|
| MONITOR-04 | `alerts.created_at` dual-format corruption (T-separator vs space-separator) prevented correct temporal comparisons | Migration 004 canonicalized all 438 existing rows to `'YYYY-MM-DD HH:MM:SS.ffffff'` space-separator format | **10.1-03** |
| MONITOR-05 | BACKTEST contamination: `pipeline_runs_last_24h` counted 1442 BACKTEST rows → 1447 total, masking LIVE=0 condition | Added `AND mode = 'LIVE'` filter to `get_alerts_pipeline_health()` pipeline_runs COUNT query | **10.1-04** |
| MONITOR-06 | `find_open_alert` dedup window broken across calendar-day boundaries (T-format vs space-format mismatch pre-migration) | Regression test coverage added for boundary-day case; root fix was migration 004 (MONITOR-04) | **10.1-05** |
| MONITOR-07 | Slack retry dead code: `except (URLError, OSError)` catch-all swallowed `HTTPError` (4xx/5xx) silently; no `Retry-After` 429 handling | Rewrote `send_meta_alert` retry loop: `HTTPError` vs `URLError` distinguished, 429 `Retry-After` honored, 5xx exponential backoff, 4xx non-retriable logged | **10.1-06** |
| MONITOR-08 | `alerts_written_count` over-counted: set to `1` when `alert_triggered=True`, but dedup UPDATE path also sets `alert_triggered=True` without inserting a new row | Extracted `_alerts_written_from_result()` helper reading `delivery_status.db_new_row` — INSERT→1, UPDATE/dedup→0 | **10.1-07** |
