## Implementation Decisions (LOCKED — from auditor synthesis)

### D-10.1-01 — Canonical `created_at` format = **naive UTC ISO with microseconds, space separator**: `'2026-04-24 11:58:42.123456'`
**Rationale:** SQLite `datetime('now', '-1 day')` and `datetime('now')` produce space-separator naive UTC. Aligning to that format makes string comparisons correct WITHOUT strftime wrappers or format conversions in queries. Python side: use `datetime.utcnow().strftime('%Y-%m-%d %H:%M:%S.%f')` or `datetime.utcnow().isoformat(sep=' ', timespec='microseconds')`.
**Alternative rejected:** Aware `+00:00` format — `+` (ASCII 43) sorts below digits (48-57), breaks `MAX(created_at)` across mixed-format rows. Even if we normalized everything to aware format, SQLite `datetime('now')` still returns naive → format mismatch on every 24h query.

### D-10.1-02 — Existing 438 alerts rows: **migrate in-place to canonical format**
**Rationale:** Leaving 2 formats in the table indefinitely would require format-aware queries everywhere. Migration 004 normalizes all existing rows in a transaction with ledger guard (same pattern as migration 001/002/003).
**Scope:** `alerts.created_at` only. `pipeline_runs.created_at` is already clean (all rows written via same code path). Verify before migration.

### D-10.1-03 — Callers of `datetime.utcnow().isoformat()` and `datetime.now(timezone.utc).isoformat()` all get grepped and unified
**Callsites to audit:**
- `backend/notifier/` (aware format) — switch to naive canonical
- `backend/db/operations.py::create_alert` (naive with microseconds T-separator) — switch to naive canonical space-sep
- `backend/db/operations.py::record_pipeline_run` — verify already canonical
- `scripts/backfill_alerts.py` — verify already canonical
- Tests + helpers that assert created_at format — update to canonical

### D-10.1-04 — Silent-failure watchdog query gets TWO fixes in one change
`get_alerts_pipeline_health()` in `backend/db/operations.py`:
1. `AND mode = 'LIVE'` added to the `pipeline_runs` count query
2. Temporal comparison: since D-10.1-01 makes all created_at space-sep, the existing `datetime('now','-1 day')` comparison becomes correct automatically. VERIFY via test that same-calendar-day T-format strings (from legacy mixed rows, pre-migration) would have failed — then confirm post-migration it passes.

### D-10.1-05 — `find_open_alert` fix path
Same root cause as watchdog (T-vs-space). Post-D-10.1-01 + migration 004, dedup window automatically corrects. No code change in `find_open_alert` itself — migration is the fix. Add a regression test that creates a 7-hour-old open alert across a calendar-day boundary and asserts `find_open_alert` returns None.

### D-10.1-06 — Slack retry rewrite (MONITOR-07)
Replace current `except (URLError, OSError)` catch-all with:
```python
try:
    with urlopen(request, timeout=10) as resp:
        if resp.status == 200:
            return True
        # urlopen() raises HTTPError for non-2xx, so this line is only reached on rare implementations that return non-exception non-2xx
except urllib.error.HTTPError as e:
    if e.code == 429:
        retry_after = e.headers.get('Retry-After', '60')
        backoff = int(retry_after) if retry_after.isdigit() else 60
        logger.warning("Slack 429 rate-limit, sleeping %ds", backoff)
        time.sleep(backoff)
        continue  # retry
    elif e.code >= 500:
        # transient server error, retry with exponential backoff
        continue
    else:
        # 4xx client error (except 429): not retriable
        logger.error("Slack 4xx non-retriable: %d %s", e.code, e.reason)
        return False
except urllib.error.URLError as e:
    # network layer: DNS, connection refused, timeout → retry
    logger.warning("Slack network error, retrying: %r", e)
    continue
```
Keep 3 total attempts, exponential backoff base 1s on 5xx/URLError, `Retry-After` honored on 429.

### D-10.1-07 — Counter semantics fix (MONITOR-08)
`backend/scheduler/scheduler.py:68` currently sets `alerts_written_count=1` on `alert_triggered=True`. But the notifier dedup path may `UPDATE` an existing alert (no new row). Fix: track `alert_written_new` boolean returned from the notifier indicating whether it INSERTed (1) or UPDATEd (0). `record_pipeline_run(..., alerts_written_count=alert_written_new)`.
**Affects:** notifier return signature + scheduler call site + backfill_alerts (already tracks true writes correctly per Auditor A).
