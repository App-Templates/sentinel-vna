# Phase 10.1: Code Review Report

**Reviewed:** 2026-04-24
**Depth:** standard
**Files Reviewed:** 13

## Summary

Phase 10.1 delivers a coherent set of fixes addressing the MONITOR-04..08 audit
findings: migration 004 canonicalizes `alerts.created_at` rows, write paths in
`notifier.py` + `operations.py` are unified to the canonical space-sep naive UTC
microseconds format, the silent-failure watchdog Slack retry loop is rewritten
with proper `HTTPError` / `URLError` distinction and Retry-After handling, and
the scheduler counter semantics switch from `alert_triggered` to the
`db_new_row` INSERT signal. The HARD-03 drift gate in `test_models_sync.py`
(`TestCreatedAtFormatInvariant`) is a welcome guardrail that enforces the new
contract at commit time.

One critical finding stands out: `notifier.send_daily_digest` queries
`pending_notifications` with a cutoff built from aware T-separator
`datetime.now(timezone.utc).isoformat()`, while writes to that same table go
through `_canonical_utc_now()` (naive space-sep). This is exactly the bug class
migration 004 fixed for `alerts.created_at`, and it will intermittently drop
P1/P2 alerts from the daily digest because the string compare
`'2026-04-24 12:00:00.000000' >= '2026-04-24T12:00:00+00:00'` is False
(`' ' (0x20) < 'T' (0x54)`). Easy fix, same pattern as the rest of the phase.

A small cluster of warnings cover unbounded Retry-After sleeps, a narrow
auto-restore window in the migration driver, a negative-offset gap in the
migration SQL, and `update_alert_status` / `create_event` still using
non-canonical timestamps (acknowledged by the inline NOTE but worth tracking
for Phase 10.2).

## Critical Issues

### CR-01: `send_daily_digest` cutoff format mismatches `pending_notifications.created_at` write format

**File:** `backend/agents/notifier.py:582` (read) and `backend/agents/notifier.py:67` (write)
**Issue:**

`_save_to_pending_notifications` writes `created_at` in canonical space-sep
naive UTC microseconds format via `_canonical_utc_now()` (e.g.
`'2026-04-24 12:00:00.123456'`). But `send_daily_digest` builds the cutoff
with:

```python
cutoff = (datetime.now(timezone.utc) - timedelta(hours=24)).isoformat()
# → '2026-04-23T12:00:00.123456+00:00'
```

and runs `WHERE created_at >= ?` against the space-sep column. SQLite does a
byte string compare; `' '` (0x20) sorts BELOW `'T'` (0x54), so any row written
on the canonical path compares BELOW a same-instant aware-T cutoff. Concretely:

```
'2026-04-24 00:00:00.000000' >= '2026-04-23T00:00:00.000000+00:00'  → FALSE
```

because the first character that differs is position 10 (`' '` vs `'T'`), and
space loses. Result: for the first ~20 hours of the day, the digest WHERE
clause excludes the freshly-queued row even when the row was written strictly
AFTER the 24h cutoff. This is the same bug class as MAJOR-NEW-01 that migration
004 fixed for `alerts.created_at` — it has been left unfixed in the digest
query.

Impact: P1/P2 alerts silently dropped from the daily digest on the day they
fire, reappearing only once the cutoff rolls past the T-separator ambiguity
window. The digest itself also DELETEs matched rows with the same faulty
WHERE, so the bug is self-healing across days but hides alerts for one cycle.

**Fix:**

Replace both the cutoff construction and the DELETE clause with the same
helper used for writes, so read and write paths use byte-identical format:

```python
# near top of notifier.py alongside _canonical_utc_now:
def _canonical_utc_cutoff(hours_ago: int) -> str:
    return (datetime.utcnow() - timedelta(hours=hours_ago)) \
        .isoformat(sep=' ', timespec='microseconds')

# in send_daily_digest:
cutoff = _canonical_utc_cutoff(24)

with get_db() as conn:
    rows = conn.execute(
        """SELECT alert_id, severity, channel_group, timestamp
           FROM pending_notifications
           WHERE created_at >= ?
           ORDER BY created_at DESC""",
        (cutoff,),
    ).fetchall()
...
with get_db() as conn:
    conn.execute(
        "DELETE FROM pending_notifications WHERE created_at >= ?",
        (cutoff,),
    )
```

Alternatively, use SQLite-native comparison (`WHERE created_at >=
datetime('now', '-1 day')`) which yields the same canonical space-sep format
the writer uses. Either way, extend the HARD-03 drift gate
(`TestCreatedAtFormatInvariant`) to cover `send_daily_digest` so a regression
here is caught at commit time — the current gate explicitly scopes it out
which is why this one slipped through.

## Warnings

### WR-01: Migration 004 SQL does not handle negative timezone offsets

**File:** `scripts/migrations/004_canonicalize_alerts_created_at.sql:62-73`
**Issue:**

Pattern A matches aware T-format via `WHEN created_at LIKE '%T%' AND
created_at LIKE '%+%'`. The `+` literal only matches positive offsets
(`+00:00`). A timestamp with a negative offset like
`'2026-04-23T21:42:50-03:00'` fails Pattern A, falls through to Pattern B
(`LIKE '%T%' AND LIKE '%.%'`), and — if it has microseconds — gets a naive
`T → ' '` swap. The result leaves the trailing `-03:00` suffix intact:
`'2026-04-23 21:42:50.142222-03:00'`. This is NOT canonical and would fail
the post-apply regex check `^\d{4}-\d{2}-\d{2} \d{2}:\d{2}:\d{2}\.\d{6}$`,
which would trigger auto-restore — safe but wasteful of one apply cycle.

The comment block at the top of the SQL notes "live data is UTC-only (Phase
07/09 audit confirmed)" so in practice this is theoretical. But the
apply-and-restore loop would still burn a failed apply on the first negative
offset encountered.

**Fix:**

Either defensively handle `-` offsets (detect via `instr(created_at,'T') > 0
AND (instr(substr(created_at, instr(created_at,'T')), '+') > 0 OR
instr(substr(created_at, instr(created_at,'T')), '-') > 0)`), or add an
explicit guard UPDATE that fails the transaction with a descriptive error if
any row post-SUBSTR still contains `+` or `-` after position 10:

```sql
-- After the UPDATE, before COMMIT, validate:
SELECT CASE WHEN EXISTS (
    SELECT 1 FROM alerts
    WHERE created_at LIKE '%+%' OR substr(created_at, 11) LIKE '%-%'
) THEN RAISE(ABORT, 'migration 004: offset residue detected') END;
```

Keeps the "live is UTC" contract explicit in-SQL, fails fast inside the same
transaction so auto-restore doesn't even need to kick in.

### WR-02: Unbounded `Retry-After` sleep in `send_meta_alert`

**File:** `backend/monitoring/silent_failure_watch.py:150-161`
**Issue:**

```python
if e.code == 429:
    retry_after = e.headers.get("Retry-After", "")
    try:
        backoff = int(retry_after) if retry_after.isdigit() else (2 ** attempt)
    except Exception:
        backoff = 2 ** attempt
    if attempt < max_retries - 1:
        ...
        time.sleep(backoff)
```

`retry_after` is trusted without a cap. A misconfigured or malicious upstream
returning `Retry-After: 9999999` would sleep the watchdog for ~116 days,
blocking subsequent watchdog cycles behind `max_instances=1`. While unlikely
against `hooks.slack.com`, the watchdog is the last line of defense for
silent failures; starving it in a retry loop defeats its purpose.

Secondary: `Retry-After` can also be an HTTP-date per RFC 7231 (not just a
delta-seconds integer). Current code only accepts the delta-seconds form
(`.isdigit()`), falling back to exponential. That fallback is safe, but note
the branch is unreachable for HTTP-date responses.

**Fix:**

Cap the backoff at the watchdog interval or a tight constant (e.g. 300s = 5
minutes, well under the 60m cron). If a legitimate retry needs longer, let
the next cycle handle it:

```python
MAX_BACKOFF_SEC = 300

if e.code == 429:
    retry_after = e.headers.get("Retry-After", "") if e.headers else ""
    try:
        backoff = min(int(retry_after), MAX_BACKOFF_SEC) if retry_after.isdigit() else (2 ** attempt)
    except Exception:
        backoff = 2 ** attempt
```

### WR-03: `_restore` has a narrow window where live DB is absent

**File:** `scripts/apply_migration_004.py:178-195`
**Issue:**

```python
def _restore(bak: Path, dst: Path) -> None:
    for suffix in ("-wal", "-shm"):
        stale = dst.with_name(dst.name + suffix)
        if stale.exists():
            stale.unlink()

    if dst.exists():
        dst.unlink()                   # <-- dst now missing

    bak_conn = sqlite3.connect(str(bak))
    dst_conn = sqlite3.connect(str(dst))   # creates empty dst
    try:
        bak_conn.backup(dst_conn)
    finally:
        dst_conn.close()
        bak_conn.close()
```

If the driver is killed (SIGKILL, power loss, OOM) between `dst.unlink()` and
`bak_conn.backup()` completing, the live DB is either absent or empty. The
.bak is intact, so recovery is a manual `cp`, but the system is left without
a DB file until an operator intervenes.

This matters for this specific driver because the driver only invokes
`_restore` from an already-failing path (apply or verify failure) — a second
failure here compounds the incident.

**Fix:**

Restore to a temp path alongside the live DB, then atomic-rename over the
live file only on success. `os.replace` is atomic on POSIX for same-filesystem
moves:

```python
def _restore(bak: Path, dst: Path) -> None:
    for suffix in ("-wal", "-shm"):
        stale = dst.with_name(dst.name + suffix)
        if stale.exists():
            stale.unlink()

    tmp = dst.with_suffix(dst.suffix + ".restore.tmp")
    if tmp.exists():
        tmp.unlink()

    bak_conn = sqlite3.connect(str(bak))
    dst_conn = sqlite3.connect(str(tmp))
    try:
        bak_conn.backup(dst_conn)
    finally:
        dst_conn.close()
        bak_conn.close()

    os.replace(tmp, dst)   # atomic same-fs rename; dst always points to a valid DB
    _log(f"Restored {dst} from {bak} via sqlite3.backup() + atomic replace")
```

### WR-04: `update_alert_status` + `create_event` still write non-canonical `updated_at` / `timestamp`

**File:** `backend/db/operations.py:174` and `backend/db/operations.py:220`, `237`, `252`
**Issue:**

After migration 004 normalizes all 438 existing `alerts.created_at` rows,
`update_alert_status` still writes `updated_at = datetime.utcnow().isoformat()`
which produces a T-separator (`'2026-04-24T12:00:00.123456'`). Every ACK /
RESOLVE / SNOOZE transition reintroduces a non-canonical value into an alert
row.

Comments in `create_event` and `create_recheck` explicitly call this out as
"NOT in D-10.1-01 scope" — fair for those tables. But `update_alert_status`
writes into the same `alerts` table that migration 004 just canonicalized.
The `updated_at` column is not currently compared by `get_alerts_pipeline_health`
or `silent_failure_watch`, so no live bug today — but the drift gate
(`TestCreatedAtFormatInvariant`) only checks write paths, not `update_alert_status`,
so this regression would not be caught.

Also: migration 004 only touches `alerts.created_at`, not `alerts.updated_at`.
Pre-migration `updated_at` rows are mixed-format too; post-migration, they
remain mixed. If a future query joins or compares these two columns, the
MAJOR-NEW-01 bug class resurfaces.

**Fix:**

Use the canonical form in `update_alert_status`:

```python
def update_alert_status(alert_id: str, new_status: AlertStatus) -> bool:
    now = datetime.utcnow().isoformat(sep=' ', timespec='microseconds')
    with get_db() as conn:
        cursor = conn.execute(
            "UPDATE alerts SET status = ?, updated_at = ? WHERE alert_id = ?",
            (new_status.value, now, alert_id),
        )
    ...
```

Extend `TestCreatedAtFormatInvariant` to assert
`update_alert_status` body contains `.isoformat(sep=' ', timespec='microseconds')`
and does NOT contain bare `.isoformat()`. Add a Phase 10.2 entry for migrating
`alerts.updated_at` rows + expanding migration coverage to the sibling
timestamp columns (`alert_events.timestamp`, `recheck_queue.scheduled_at`) that
the code comments already flag.

### WR-05: `scheduler.start_scheduler` crashes if `config.silent_failure_monitor` is absent on older configs

**File:** `backend/scheduler/scheduler.py:290, 311`
**Issue:**

```python
if config.silent_failure_monitor.enabled:
    ...
silent_failure_info = ""
if config.silent_failure_monitor.enabled:
    ...
```

Accessed without a defensive guard. If a deployment rolls out with a
`config_loader` that does not contain `silent_failure_monitor` (old checkout,
partial deploy, hotpatched config), `AttributeError` propagates out of
`start_scheduler` and the whole scheduler fails to start — no A1/A3 cycles,
no rechecks, no digest. The pipeline goes dark.

The watchdog is a belt-and-suspenders guardrail. It should never gate the
entire scheduler on its own config key existing.

**Fix:**

Guard the access:

```python
try:
    silent_failure_enabled = config.silent_failure_monitor.enabled
except AttributeError:
    logger.warning("silent_failure_monitor not configured; skipping watchdog")
    silent_failure_enabled = False

if silent_failure_enabled:
    scheduler.add_job(run_watch_cycle, ...)
```

### WR-06: `_resolve_webhook_url` has no hard fallback for missing Retry-After header object

**File:** `backend/monitoring/silent_failure_watch.py:151`
**Issue:**

`e.headers.get("Retry-After", "")` — real `urllib.error.HTTPError` instances
always carry a `headers` attribute (email.message.Message), so `.get()` is
safe. But test doubles sometimes return `None` for `e.headers`, and the
`send_meta_alert` function documents itself as "never raise -- silent-failure
watchdog must never crash the scheduler".

If `e.headers` is None for any reason, `None.get(...)` raises AttributeError.
That AttributeError propagates out of the `except urllib.error.HTTPError`
block because there is no inner try/except — it would land in `run_watch_cycle`
which has a broad `try/except Exception`, so the scheduler survives, but
`run_watch_cycle` records a generic `watchdog_error` for what is actually a
silent-failure detection that the watchdog should have retried.

**Fix:**

Defensive:

```python
headers = e.headers or {}
retry_after = headers.get("Retry-After", "") if hasattr(headers, "get") else ""
```

Or wrap the header access in its own try/except. Low probability in prod; easy
to harden.

## Info

### IN-01: `_canonical_utc_now` uses deprecated `datetime.utcnow()`

**File:** `backend/agents/notifier.py:39` (and widely throughout the codebase)
**Issue:** `datetime.utcnow()` is deprecated as of Python 3.12 in favor of
`datetime.now(timezone.utc)`. The deprecation will become a DeprecationWarning
emit-on-import in future versions. The whole codebase uses `.utcnow()`
consistently — fine as a single unit of refactor.
**Fix:** Schedule a sweep that replaces all `datetime.utcnow()` with
`datetime.now(timezone.utc).replace(tzinfo=None)` where the existing contract
is naive, or with the aware form where appropriate. Keep the canonical helper
the single source of truth.

### IN-04: `_send_email` cannot send to comma-separated recipient list

**File:** `backend/agents/notifier.py:463, 476, 490`
**Issue:**
```python
email_to = os.environ.get("ALERT_EMAIL_TO")   # single string
...
msg["To"] = email_to
...
server.sendmail(smtp_user, [email_to], msg.as_string())
```
If an operator configures `ALERT_EMAIL_TO=ops@x.com,oncall@x.com` expecting
multi-recipient behavior, the SMTP envelope is `["ops@x.com,oncall@x.com"]` —
one invalid RFC822 address — and SMTP servers will reject or drop silently.
Not a bug per the current contract (single address), but brittle.
**Fix:** Split on `,` and strip: `[addr.strip() for addr in email_to.split(",")
if addr.strip()]`. Document the multi-recipient support in a comment.

### IN-05: `SMTP_PORT` parse before configuration-presence check

**File:** `backend/agents/notifier.py:460-466`
**Issue:**
```python
smtp_port = int(os.environ.get("SMTP_PORT", "587"))   # ← ValueError if non-numeric
smtp_user = os.environ.get("SMTP_USER")
...
if not all([smtp_host, smtp_user, email_to]):
    logger.info("Email not configured, skipping")
    return False
```
If an operator sets `SMTP_PORT=abc` in an environment where email is NOT
configured (missing `SMTP_HOST`), `int("abc")` raises BEFORE the
`if not all(...)` guard has a chance to short-circuit and return False. The
notifier bubbles the ValueError into `notifier_agent.except Exception`, which
is swallowed, but the log line is `"Email send failed: ..."` rather than
`"Email not configured, skipping"`.
**Fix:** Move `smtp_port = int(...)` AFTER the `all(...)` guard, or wrap in
try/except ValueError.

### IN-06: `notifier.send_daily_digest` reads the webhook URL from plaintext YAML

**File:** `backend/agents/notifier.py:563-573`, `config/alerting_rules.yaml:154`
**Issue:** The Slack webhook URL
(`https://hooks.slack.com/services/TEST123`) is stored in plain text in
`config/alerting_rules.yaml` which is committed to git. Slack incoming-webhook
URLs are credentials (anyone with the URL can post as the app). The placeholder
`TEST123` looks like a scaffold value, which is acceptable for this phase, but
the env-var override path (`SLACK_WEBHOOK_URL`) should be the documented prod
mechanism and the YAML field should be `null` (or the loader should refuse to
use the YAML value in prod). Same concern applies to
`silent_failure_monitor.slack_channel_override`.
**Fix:** In `config/alerting_rules.yaml`, set `slack_notifications.webhook_url:
null` and keep the env-var path as the sole prod ingress. Add a prod-mode
assertion in `config_loader` that refuses to start if the YAML webhook is
non-null AND `SLACK_WEBHOOK_URL` env is also set (operator should pick one,
not both). This also eliminates the test-vs-prod ambiguity where the scheduler
might quietly post to `TEST123` if the env var is forgotten.
