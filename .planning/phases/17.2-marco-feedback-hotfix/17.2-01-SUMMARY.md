# Phase 17.2 Plan 01: V3 Tooltip Discriminant Fix Summary

**RevenueTrendChart Tooltip formatter now uses `item.dataKey === 'revenue'` (not `name === 'revenue'`) to discriminate current vs baseline series — fixes "Baseline on both rows" bug Marco reported 2026-05-19.**

## Accomplishments

- Bug V3 root cause confirmed verbatim against source (line 65-68 pre-fix): the recharts Tooltip formatter compared `name === 'revenue'` against the `<Line name="Current Revenue">` / `<Line name="Baseline">` display-label strings (never against the dataKey). Comparison was always false → both rows rendered "Baseline".
- Fixed in-place with a 8-line block edit (formatter rewritten + 8-line intent comment): `(value, _name, item) => [formatCurrency(...), (item as {dataKey?: string} | undefined)?.dataKey === 'revenue' ? 'Current Revenue' : 'Baseline']`.

- 1 atomic commit, single-file diff (12 insertions, 2 deletions).

## Files Created/Modified

- `frontend/src/components/charts/RevenueTrendChart.tsx` — Tooltip formatter callback rewritten to discriminate via `item.dataKey` (3rd formatter arg) instead of the 2nd arg `name` (which recharts populates from the `<Line name>` display-label prop, not the dataKey). 8-line intent comment added explaining the root cause for future maintainers.

## Before vs After (the 5-line behavior fix)

**Before** (`RevenueTrendChart.tsx:65-67` pre-fix):
```tsx
formatter={(value, name) => [
  formatCurrency(Number(value)),
  name === 'revenue' ? 'Current Revenue' : 'Baseline',
]}
```
Bug: `name` is `"Current Revenue"` or `"Baseline"` (Line display label) — never `"revenue"`. The ternary's truthy branch was unreachable → both rows rendered `"Baseline"`.

**After** (`RevenueTrendChart.tsx:73-77` post-fix):
```tsx
formatter={(value, _name, item) => [
  formatCurrency(Number(value)),
  (item as { dataKey?: string } | undefined)?.dataKey === 'revenue'
    ? 'Current Revenue'
    : 'Baseline',
]}
```
Fix: `item.dataKey` is the actual series identifier (`'revenue'` for current, `'baseline'` for baseline), set by the `<Line dataKey="...">` prop. Now both branches of the ternary are reachable.

## Decisions Made

- **Option 1 (item.dataKey) over Option 2 (compare-against-name-display-string):** The plan offered two safe fixes — switch the discriminant target to `item.dataKey` (Option 1) or change the compared string to match the display label (`name === 'Current Revenue'`, Option 2). Picked Option 1 per the plan's recommendation: Option 1 decouples the discriminant from the human-readable label, so a future rename of the `<Line name>` prop (i18n, A/B label test, marketing rewrite) does not re-introduce the same bug class.
