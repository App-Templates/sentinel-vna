# Phase 17.2 Plan 05: Triage Bacino + Coverage Fix Summary

Contract drift fix on TriageSection.tsx: read `bacino_current` / `coverage_current` (the actual per-env payload keys emitted by environment_splitter) instead of the non-existent `bacino` / `coverage` keys. Marco's "Bacino + Coverage = 0 su tutti gli alert" was caused by `m.bacino ?? 0 = 0` across 100% of alerts — not by empty env_split as the plan's leading hypothesis suggested.

## Objective

Close HOTFIX-05 (B2 from Marco Manduca's email 2026-05-19): the AlertDetailPage Tab 2 Triage Classification table showed "Bacino (Impressions)" and "Coverage" = 0 on every alert. The plan structured the work as diagnose-first → fix because the underlying hypothesis space included (i) empty env_split dominant cohort, (ii) populated env_split with missing baseline sub-fields, (iii) frontend rendering bug. The fix path was deliberately left undetermined until the diagnosis confirmed which hypothesis was actually live.

## Diagnosis result (Task 1)

**Plan's leading hypothesis (i) was falsified by the data.** All 238 snapshot alerts (`frontend/dist/api/alerts/ALT-*.json`) have:

- `environment_split` POPULATED with 3 per-env dicts (WEB, AMP, APP) plus `amp_drift_detected: true` scalar
- `baseline_bacino` non-null at top level (server-computed by Phase 11 API-03)
- `baseline_coverage` non-null at top level (server-computed by Phase 11 API-03)
- Per-env metrics keys: `revenue_current`, `revenue_baseline`, `delta_abs`, `delta_pct`, `bacino_current`, `bacino_baseline`, `coverage_current`, `coverage_baseline`

**Root cause = HYPOTHESIS (iii) variant — contract drift on `_current` suffix.** The producer (`backend/agents/environment_splitter.py:42-50`) emits per-env metrics with the `_current` suffix; the consumer (`frontend/src/components/alerts/TriageSection.tsx:43-46`) was reading `m.bacino` / `m.coverage` — undefined on every payload → `?? 0` fallback → literal "0" on every alert. The baseline column rendered correctly because the top-level `alert.baseline_bacino` / `alert.baseline_coverage` fields DO match the contract. Marco's report ("tutti = 0") was specifically the current column being uniformly 0; the baseline column was actually showing real numbers, but the visual pattern across 238 alerts was dominated by the failed current column.

Diagnosis decision: **Path C** (corrected from the plan's binary A/B framing):

1. **Primary (root-cause):** read `m.bacino_current` and `m.coverage_current`
2. **Defensive (Path B leftover):** keep `envSplitMissing` predicate + 'n/a' substitution + disclosure copy as a safety net for hypothetical empty-env_split alerts (legacy pre-Phase-11 surfaced via `?include_deprecated=true`, or future splitter run failures)
3. **Out of scope:** EnvironmentSplitSection.tsx (Tab 5) and EnvironmentBarChart same-class drift on `metrics.revenue` / `metrics.bacino` / `metrics.coverage` / `metrics.baseline_revenue` / `metrics.delta_percent` — flagged for Phase 17.3 or future HOTFIX-08 (not HOTFIX-05's mandate)

  ? (Object.entries(alert.environment_split) as [Environment, EnvironmentMetrics][])

## Deviations from Plan

The plan presented hypothesis (i) ("empty env_split dominant cohort, frontend reduce over [] produces 0") as the "most LIKELY" cause and pre-described Path B (frontend-only n/a substitution) as the recommended fix. The diagnosis FALSIFIED hypothesis (i) — 0% of the 238 snapshot alerts had empty env_split. The actual root cause is a different class of bug: contract drift on the `_current` suffix between producer and consumer.

### [Rule 1 — Bug] Read `_current` suffix instead of bare key

- **Found during:** Task 1 diagnosis (inspected representative + Marco's 2 specific alerts, confirmed across full 238-alert corpus)
- **Issue:** TriageSection.tsx reads `m.bacino` / `m.coverage`; payload emits `bacino_current` / `coverage_current`. `m.bacino === undefined` → `?? 0` → "0" on every alert.
- **Fix:** Read `(m as {bacino_current?: number}).bacino_current ?? m.bacino ?? 0` (and analogously for coverage). Narrow per-aggregation casting rather than wholesale `EnvironmentMetrics` interface rename — keeps blast radius minimal (Tab 5 same-class drift left explicitly for Phase 17.3 candidate, per diagnosis decision).
- **Files modified:** `frontend/src/components/alerts/TriageSection.tsx`
- **Commit:** `f0a7303`

### [Rule 1 — Bug] Filter `amp_drift_detected` out of envEntries

- **Found during:** Task 2 implementation (surfaced while wiring the new aggregation)
- **Issue:** `Object.entries(environment_split)` yields `["amp_drift_detected", true]` as one entry alongside the 3 env dicts. `envEntries.length` is then 4. The boolean entry contributes 0 to both sums (since `typeof true !== 'object'` and the lookup returns undefined), BUT the divisor `envEntries.length = 4` dilutes `avgCoverage` by 1/4 (~25% understatement).
- **Fix:** `envEntries = envEntriesRaw.filter(([, v]) => typeof v === 'object' && v !== null)` — restricts iteration to the 3 actual env dicts. `envEntries.length === 3`, divisor is correct.
- **Files modified:** `frontend/src/components/alerts/TriageSection.tsx`
- **Commit:** `f0a7303`

### [Plan deviation — diagnosis result drove Path C, not Path B]

- **Found during:** Task 1 diagnosis (data inspection contradicted plan's leading hypothesis)
- **Issue:** Plan recommended Path B (frontend-only `'n/a'` substitution for empty env_split). The data shows that path would never fire on real alerts (0% empty env_split). Marco would still see "0" after a Path B-only fix.
- **Fix:** Path C — root-cause field-name fix PLUS defensive Path B layer kept as safety net. The plan's must_haves (envSplitMissing predicate + 'n/a' substitution + disclosure copy) are all satisfied; an additional root-cause fix is layered on top.
- **Files modified:** `frontend/src/components/alerts/TriageSection.tsx`
- **Commit:** `f0a7303` (single GREEN commit — Path C is conceptually two paths but mechanically one render-time change to the same lines)
