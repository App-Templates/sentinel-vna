## Root Cause Hypothesis

Ranked by likelihood (most likely first). Each hypothesis cites specific
evidence rows from the block above.

### H1 (HIGH CONFIDENCE) — Parquet data frozen at 2026-03-23 blocks fresh alerts

**Claim:** The LIVE pipeline produces zero new alerts because
`daily_aggregated.parquet` has `max_date=2026-03-23`, identical to
`MAX(alerts.created_at)=2026-03-23 13:00:00`. The scheduler runs, data_fetcher
loads the same bounded window repeatedly, anomaly_detector correctly concludes
"no change vs baseline" on the tail date, and triage emits `no_alert`.

**Supporting evidence:**

- Evidence §6 `parquet.max_date = 2026-03-23` (days_since_max = 32 vs today 2026-04-24)
- Evidence §1 `MAX(alerts.created_at) WHERE deprecated=0 = 2026-03-23 13:00:00.000000`
- Evidence §5 `data_source` histogram = `{backfill: 238}` — zero `real_parquet`, zero `live`
- Evidence §4 status distribution = `{no_alert: 2590, ok: 1}` — 99.96% of LIVE runs emitted `no_alert`

**Why 2026-03-23 is the exact cutoff:** Phase 09 backfill orchestrator wrote
238 alerts with `data_source='backfill'` spanning 2026-01-23 → 2026-03-23
(Evidence §1 MIN=2026-01-23 01:00:00 / MAX=2026-03-23 13:00:00). No LIVE
alerts have EVER been written since v1.2 shipped 2026-03-26 — Evidence §5
confirms zero `real_parquet` / `live` rows among the 238 fresh alerts. The
`GOOGLE` + `OPEN_BIDDING` LIVE runs (Evidence §3) would produce no-alert
outcomes against a stale window even if the pipeline were running on fresh
dates.

**Remediation ownership:** NOT 999.1. Parquet refresh is the explicit
`.planning/phases/09-alert-backfill-legacy-migration/COVERAGE-GAP.md` Option
A / Option B plant-seed for Phase 11 / v1.3.1. Re-running
`scripts/etl_csv_to_parquet.py` would invalidate Phase 08 Plan 05 Mondadori
fill-rate checksums (see COVERAGE-GAP.md §"Gap", bullets 3a–3c) and is
explicitly out of scope for Phase 999.1.

### H2 (MEDIUM CONFIDENCE) — Legacy scheduler channel list + unconstrained channel_group column

**Claim:** Two observations make this hypothesis MEDIUM, not LOW, confidence:

1. The `uvicorn` / scheduler process that ran 2026-02-15 → 2026-04-22 was
   reading an older `config.scheduling.channels` list (legacy
   `['GOOGLE', 'OPEN_BIDDING']` — see Evidence §3 `observed` DISTINCT),
   not the current 7-channel v1.2 list (Evidence §3 `configured` =
   `['GOOGLE_ADEX', 'OPEN_BIDDING', 'HEADER_BIDDING_MAGNITE',
   'HEADER_BIDDING_PUBMATIC', 'TAM', 'DIRECT', 'DEAL']`). That process is
   now dead (Evidence §7 `running = False`, `pids = []`), so this
   sub-hypothesis only matters for the *next* scheduler restart — which
   would iterate all 7 channels per the current YAML.

2. Observed channel_group values include `mondadori` (lowercase), which is
   NOT in the `ChannelGroup` enum defined at `backend/db/models.py:33-42`
   (the enum only contains UPPERCASE values: `GOOGLE_ADEX`, `OPEN_BIDDING`,
   `HEADER_BIDDING_MAGNITE`, `HEADER_BIDDING_PUBMATIC`, `TAM`, `DIRECT`,
   `DEAL`, plus the legacy `GOOGLE` alias — Evidence §3 `app_allowed_set`).
   The live `pipeline_runs` table has NO SQL-level CHECK constraint on
   `channel_group` (confirmed by Evidence §3 `table_ddl` — the column is
   declared as `channel_group TEXT NOT NULL` with no CHECK IN (...) clause;
   the only CHECK on pipeline_runs is the Phase 10 `alerts_written_count >= 0`
   guard). Evidence §3 `per_value_flags` flags `mondadori` with
   `constraint_violation: true`, `in_enum: false`, `in_config: false`. This
   means SOMETHING writes `pipeline_runs` rows via a direct SQL path that
   does not go through the `ChannelGroup` enum check. The prime suspect is
   the Plan 10.1-08 smoke test: Evidence §2 `MAX(timestamp) = 2026-04-23T21:27:19.538588`
   with `channel_group = 'mondadori'` — a single row consistent with the
   smoke-test terminus, not with scheduler traffic. The real-scheduler
   terminus sits at Evidence §2 `2nd-MAX = 2026-04-22T09:18:20.696035` with
   `channel_group = OPEN_BIDDING`. Investigate whether Plan 10.1-08
   intentionally used a distinct test channel marker OR whether there is
   drift between `backend/db/models.py` DDL template and live schema (the
   DDL template also has no CHECK on `pipeline_runs.channel_group` — see
   the `interfaces` block of `999.1-01-PLAN.md`).

When the scheduler restarts with the current YAML, it will iterate all 7
channels — but even with 7 channels, stale parquet still yields no_alert
(subordinate to H1).

**Supporting evidence:**

- Evidence §3 `observed = ['GOOGLE', 'OPEN_BIDDING', 'mondadori']`
- Evidence §3 `app_allowed_set` = 8-value enum (7 canonical + 1 legacy alias)
- Evidence §3 `per_value_flags[mondadori].constraint_violation = true`
- Evidence §3 `table_ddl` shows `channel_group TEXT NOT NULL` (no CHECK)
- Evidence §7 `running = False` → gap between 2nd-MAX 2026-04-22 09:18 and
  today (2026-04-24) indicates the scheduler process died and was not
  restarted

**Remediation ownership:** NOT 999.1 directly. Restarting the scheduler
with fresh config is a deploy-time concern (operator action, R-05 OK
required). Adding a SQL CHECK constraint to `pipeline_runs.channel_group`
is a Phase 10.2+ hardening task. This diagnosis captures BOTH sub-issues so
the operator knows (a) a restart will change channel coverage from the
legacy 2-channel set to the current 7-channel set AND (b) channel_group
writes currently bypass the application-level enum.

### H3 (LOW CONFIDENCE) — Alert-rule logic suppresses alerts against stale tail

**Claim:** Alert rules like A1 (yesterday_comparison, -30%) and A2 (drift
regression, 14-30d window) might legitimately return no_alert against a
parquet window that is all "yesterday-flat" because the tail row is literally
stuck at 2026-03-23. This is NOT a bug — it is rules working correctly
against stale data. Subset of H1.

**Supporting evidence:**

- Evidence §4 `status = no_alert` count = 2590 of 2591 total LIVE runs
  (only the Plan 10.1-08 smoke-test row escaped `no_alert` with `status=ok`)
  — consistent with rules firing correctly on stale input

**Remediation ownership:** No remediation needed — rules are correct.

## Watchdog Semantic Correctness

The Phase 10.1-08 Case C watchdog firing is **semantically correct behavior**,
not a false positive:

- `pipeline_runs_last_24h = 1` (Evidence §2 `MAX(timestamp) = 2026-04-23T21:27:19.538588`,
  Plan 10.1-08 smoke test, `channel_group = 'mondadori'`)
- `alerts_last_24h = 0` (Evidence §1 `MAX(alerts.created_at) = 2026-03-23 13:00:00.000000`
  → >30 days old, far outside the 24h window)
- `last_alert_at = 2026-03-23 13:00:00.000000` (Evidence §1)

The watchdog detected a genuine silence. The override accepted by stefano in
`.planning/phases/10.1-pipeline-monitoring-hotfix-and-hardening/10.1-VERIFICATION.md`
frontmatter `overrides[0]` documents this — the `reason` field reads verbatim:

> *"ROADMAP SC-2 assumed paired LIVE alerts exist. Live smoke correctly returned
> triggered=True (Case C: real silent failure since 2026-03-23, not a structural
> false-positive from BACKTEST contamination). Operator Stefano authorized 'C —
> flip' knowing watchdog would fire P0. This is semantically correct behavior —
> the watchdog is doing exactly what it was built to do. Deviation is from the
> assumption in SC-2, not from the requirement."*

No regression in Phase 10.1 work. The silent_failure_watchdog is doing
exactly what MONITOR-02 specified: `pipeline_runs > 0 AND alerts = 0` → P0.
That the silence is >1 month old (not the "last cycle" pattern the incident
text anticipated) does not change the math — it makes the watchdog
MORE valuable, not less.
