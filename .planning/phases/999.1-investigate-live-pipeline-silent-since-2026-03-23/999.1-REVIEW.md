## Summary

`scripts/diagnose_live_silence_999_1.py` is a 663-line read-only diagnostic
script for Phase 999.1 (MONITOR-09). It opens the live SQLite DB via
`mode=ro` URI, runs SELECT-only queries against `alerts` and
`pipeline_runs`, projects a single column from
`data/baseline/daily_aggregated.parquet`, enumerates scheduler processes
via `pgrep`, and optionally splices a Markdown evidence block into
`999.1-DIAGNOSIS.md` between explicit BEGIN/END markers.

**Read-only contract (load-bearing) — VERIFIED CLEAN:**
- `sqlite3.connect("file:...?mode=ro", uri=True)` — kernel-level RO
- No `INSERT`/`UPDATE`/`DELETE`/`DROP`/`ALTER`/`REPLACE`/`TRUNCATE`/`ATTACH`/`PRAGMA writable*`
- No `executescript()`, no `executemany()` (which still couldn't write under `mode=ro`)
- No imports of `run_pipeline`, `start_scheduler`, `run_watch_cycle`
- Transitive imports (`backend.db.models`, `backend.utils.config_loader`)
  verified module-load-side-effect-free: no DB engine init, no logging
  config, no env-var mutation
- All SQL is string-literal — zero user input concatenation, no SQL
  injection vector
- `subprocess.run` uses argv-list (no shell), 5s timeout, `check=False`,
  fail-soft try/except

**Functional correctness — TWO ISSUES FOUND:**
- A flag-interaction bug between `--json` and `--emit-markdown` causes
  the markdown write to be silently skipped when both are passed (WR-01).
- The `from backend.db.models import ChannelGroup` at line 187 is NOT
  guarded by try/except, while the symmetrical `get_config` import at
  line 193 IS guarded. A failed `ChannelGroup` import will crash the
  entire diagnostic with no fallback (WR-02).

The remaining five Info findings are minor robustness/maintainability
suggestions. The read-only contract — the most security-critical
property — is intact and well-defended.

## Warnings

### WR-01: `--json` flag silently bypasses `--emit-markdown` write

**File:** `scripts/diagnose_live_silence_999_1.py:647-651`
**Issue:** When the user passes both `--json` and `--emit-markdown PATH`,
the script returns immediately after printing JSON (line 648-649) and
never reaches `_emit_markdown()` (line 651). No warning is printed. A
user expecting both stdout JSON and a side-effect file write gets only
the former, with no diagnostic trace. Worse: if a wrapper script
expects `999.1-DIAGNOSIS.md` to be refreshed and parses the JSON for
machine consumption, it will silently use stale Markdown.

```python
if args.json:
    print(json.dumps(results, indent=2, default=str))
    return 0  # ← exits before _emit_markdown can run

block = _emit_markdown(results, args.emit_markdown)
```

**Fix:** Either (a) make the flags mutually exclusive at the argparse
level, or (b) honor both — emit JSON to stdout AND write the markdown
file. Option (b) is the principle-of-least-surprise choice for a
diagnostic tool:

```python
if args.json:
    print(json.dumps(results, indent=2, default=str))

# Always honor --emit-markdown when provided, regardless of --json
block = _emit_markdown(results, args.emit_markdown)
if args.emit_markdown:
    print(
        f"Evidence block written to {args.emit_markdown} "
        f"(between {EVIDENCE_BEGIN} / {EVIDENCE_END}).",
        file=sys.stderr,  # stderr so it doesn't pollute --json stdout
    )
elif not args.json:
    print(block)
return 0
```

Alternatively, use a mutually-exclusive group:

```python
mode = parser.add_mutually_exclusive_group()
mode.add_argument("--json", action="store_true", ...)
mode.add_argument("--emit-markdown", metavar="PATH", type=Path, ...)
```

### WR-02: Asymmetric error handling on transitive `backend.*` imports

**File:** `scripts/diagnose_live_silence_999_1.py:187, 192-200`
**Issue:** `from backend.db.models import ChannelGroup` (line 187) is
NOT wrapped in try/except, while the analogous
`from backend.utils.config_loader import get_config` (line 193) IS. If
`backend.db.models` ever grows a side-effect that fails (e.g., a
new top-level import that touches an unavailable optional dep), the
entire diagnostic crashes instead of gracefully degrading the
constraint-violation check. The docstring claim "diagnosis should
never crash" (line 196) is enforced for one import but not the other.

For a read-only forensic tool whose explicit purpose is to run AGAINST
a possibly-degraded production environment, every external import
should be hardened.

```python
# Step C: app-level allowed set (read import — respects read-only contract).
from backend.db.models import ChannelGroup  # noqa: E402  (read-only import)

app_allowed_set = [cg.value for cg in ChannelGroup]
```

**Fix:** Apply the same try/except pattern used for `get_config`:

```python
try:
    from backend.db.models import ChannelGroup  # noqa: E402
    app_allowed_set = [cg.value for cg in ChannelGroup]
    enum_error: str | None = None
except Exception as exc:
    app_allowed_set = []
    enum_error = repr(exc)

try:
    from backend.utils.config_loader import get_config  # noqa: E402
    cfg = get_config()
    configured = list(cfg.scheduling.channels)
    configured_error: str | None = None
except Exception as exc:
    configured = []
    configured_error = repr(exc)
```

And surface `enum_error` in the returned dict + Markdown formatter
(parallel to `configured_error`).

## Info

### IN-01: `with sqlite3.connect(...)` does NOT close the connection

**File:** `scripts/diagnose_live_silence_999_1.py:606-616`
**Issue:** Python's `sqlite3.Connection.__exit__` commits-or-rolls-back
the active transaction, but does NOT close the connection. The
connection is then leaked to GC, which closes it eventually but
non-deterministically. For a short-lived CLI tool this is harmless,
but the idiom is a well-known Python footgun and worth fixing for
correctness.

```python
with sqlite3.connect(uri, uri=True) as conn:
    conn.row_factory = sqlite3.Row
    return { ... }
```

**Fix:** Use `closing()` to guarantee close, or call `conn.close()`
explicitly:

```python
from contextlib import closing
with closing(sqlite3.connect(uri, uri=True)) as conn:
    conn.row_factory = sqlite3.Row
    return { ... }
```

### IN-02: `--emit-markdown` accepts arbitrary write paths with no allow-list

**File:** `scripts/diagnose_live_silence_999_1.py:623-633`
**Issue:** The `--emit-markdown` flag takes any `Path` and writes to
it (creating parent dirs via `mkdir(parents=True, exist_ok=True)`).
A user could pass `--emit-markdown /etc/anything` or
`--emit-markdown ../../../somewhere`. This is intended user behavior
(no privilege escalation — runs as the invoking user) and the script
is operator-run, not exposed to network input, so the risk is purely
foot-gun rather than security. Worth noting because the script's
read-only contract is otherwise tight.

**Fix (optional):** Constrain writes to `REPO_ROOT` if you want to
codify the invariant:

```python
out_path = Path(out_path).resolve()
try:
    out_path.relative_to(REPO_ROOT)
except ValueError:
    raise SystemExit(
        f"--emit-markdown PATH must be inside the repo: got {out_path}"
    )
```

### IN-03: Marker replacement only handles a single BEGIN/END pair

**File:** `scripts/diagnose_live_silence_999_1.py:584-589`
**Issue:** The regex uses `count=1`, so if `999.1-DIAGNOSIS.md` ever
ends up with multiple `BEGIN EVIDENCE 999.1-01 ... END EVIDENCE
999.1-01` blocks (e.g., from a half-applied edit, a merge artifact, or
an editor accident), only the first block is replaced and stale ones
remain in place. The docstring claim "overwritten deterministically"
is true for the well-formed case but silently degrades to "first
occurrence wins" otherwise.

```python
pattern = re.compile(
    re.escape(EVIDENCE_BEGIN) + r".*?" + re.escape(EVIDENCE_END),
    re.DOTALL,
)
new_text = pattern.sub(block, existing, count=1)
```

**Fix:** Detect duplicates and either fail loudly or collapse them:

```python
matches = pattern.findall(existing)
if len(matches) > 1:
    print(
        f"WARNING: {len(matches)} EVIDENCE blocks found in {out_path}; "
        f"collapsing to one.",
        file=sys.stderr,
    )
    new_text = pattern.sub(block, existing)  # replace all
    # Then remove leftover duplicates (now identical)
    parts = new_text.split(block)
    new_text = parts[0] + block + "".join(parts[1:]).replace(block, "")
else:
    new_text = pattern.sub(block, existing, count=1)
```

Or simpler — fail closed and require a manual cleanup, which is
appropriate for a diagnostic that should never lie.

### IN-04: `days_since_max` may be off-by-one across timezones

**File:** `scripts/diagnose_live_silence_999_1.py:310-319`
**Issue:** `today` is computed as `datetime.now(timezone.utc).date()`
but `max_iso` originates from the parquet's `date` column, whose
timezone semantics are implicit (the script assumes UTC date keys but
this is not asserted). If the parquet was authored with local-tz
midnight boundaries, `days_since_max` can be off by one near the
date boundary. For the H1 hypothesis ("max == 2026-03-23 pins H1 to
exact cutoff") this can flip a +0/+1/+32 reading.

**Fix:** Document the assumption in the returned dict and surface it
in the markdown table:

```python
return {
    ...
    "today_tz": "UTC",
    "max_date_tz_assumed": "UTC (parquet `date` column)",
    "days_since_max_caveat": (
        "computed as UTC-today minus parquet-date assuming both are "
        "UTC-anchored; off-by-one possible if parquet uses local tz."
    ),
    ...
}
```

Or — better — read the parquet schema and assert the date column is
`date32[day]` (not a timestamp), which sidesteps tz ambiguity:

```python
schema = pq.read_schema(DAILY_PARQUET)
date_field = schema.field("date")
assert pa.types.is_date(date_field.type), \
    f"Expected date32 for `date`, got {date_field.type}"
```

### IN-05: `pgrep -af` portability across BSD vs GNU `pgrep`

**File:** `scripts/diagnose_live_silence_999_1.py:338-344`
**Issue:** The flags `-a` (show full command line) and `-f`
(match against full argv) work on procps-ng (Linux, recent macOS) and
on macOS 12+. On older macOS or some BSDs, `-a` may not be supported
and the call returns rc=2 with empty stdout. The script's try/except
masks this as `running=False` — which is technically correct (it's
fail-soft) but misleading: "no scheduler is running" vs "pgrep flag
unsupported" are different conclusions.

**Fix:** Distinguish the two cases by checking returncode explicitly:

```python
result = subprocess.run([...], capture_output=True, text=True, timeout=5, check=False)
# pgrep returncode: 0=match, 1=no match, 2=syntax error, 3=fatal
if result.returncode >= 2:
    return {
        "running": False,
        "pids": [],
        "cmdlines": [],
        "error": (
            f"pgrep failed with rc={result.returncode}: "
            f"{result.stderr.strip()!r}"
        ),
    }
# rc 0 or 1 — proceed with parsing
```

This way, "diagnostic itself broken" surfaces in §7 instead of being
indistinguishable from "scheduler not running."
